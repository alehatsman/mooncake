# Single-Source-of-Truth Drift

The action registry, the validator's allowed-action vocabulary, the
schema generator, the docs generator, and `LLM_GUIDE.md` should all
describe the same set of actions. **They don't.** The schema and docs
generators already produce correct output — the validator is the
straggler.

One codegen fix would close most of the findings in this file.

---

## #27 — Validator's allowed-action list is out of sync with `mooncake actions list` — HIGH (structural)

**Repro**: try a top-level playbook using any of:
- `read.json`, `read.yaml`
- `text.patch.json`, `text.patch.yaml`, `text.patch.ini`, `text.line`
- `git.clone`, `git.config`, `git.checkout`
- `os.user`, `os.group`, `os.firewall`, `os.cron`, etc.
- `container`, `container.image`, `tool`, `pkg.list`, `pkg.upgrade`

All rejected at validate-time:
```
Line 1: Step must have exactly one action (shell, cmd, file.write,
  file.template, file.copy, file.download, file.unarchive, text.replace,
  text.insert, text.delete_range, text.patch, os.service, pkg,
  repo.search, repo.tree, repo.patch, artifact.capture, artifact.validate,
  assert, use, log, import, vars, vars.load, or wait)
```

But `mooncake actions list` advertises 50+ actions and `mooncake
schema generate` produces 44 action definitions including all of the
above. Confirmed via `mooncake step`: rejected actions DO exist and
DO work — they just can't be reached from a top-level playbook.

**Why HIGH (structural)**: ~half of Mooncake's typed action surface
is dead code from the playbook user's perspective. The only way to
invoke them is via `mooncake step` (subject to #22 truncation) or
the MCP `run_plan` tool.

**Likely cause**: the validator has a hardcoded vocabulary in
`internal/config/schema.json` that wasn't updated when new handlers
were registered. Validator allowlist should be auto-generated from
the registry.

**Update (round 19)**: ✅ FIXED. `mooncake validate` now reports:
```
Line 1: unknown field `nothere` (likely a typo or a renamed field
  — see docs-next/guide/config/actions.md)
Line 1: Step must have exactly one action (artifact.capture, ...,
  62 action names listed including read.json, text.patch.json,
  git.*, os.*, container, container.image, tool, transaction, try,
  windows.firewall_rule, windows.scheduled_task)
```

Vocabulary now matches `mooncake actions list`. The "renamed field"
hint pointing at the docs is a nice DX touch.

## #35 — `mooncake schema generate` produces the registry-complete schema (closes #27)

```
$ mooncake schema generate --output schema.json
$ grep -o '"[a-z]*\.[a-z_.]*": *{' schema.json | sort -u | wc -l
44
```

44 action types in the generated schema. **Every action the
validator rejects is here.**

Also supports `--format openapi` and `--format typescript`. Serious
investment in machine-readable surfaces — use it.

**Fix for #27**: replace the validator's hardcoded vocabulary with
`mooncake schema generate`'s output (or hook them to the same
source). The wiring exists; it's not connected to the validator.

## #4 — Validator anchors all errors to "Line 1" of the first step — MEDIUM (DX)

**Repro**: any playbook where a non-first step uses an action with
an invalid sub-key. Example: `file.template` with `content:`.

```
Error: /work/mooncake.yml
  Line 1: Step must have exactly one action (...)
    - vars:
    (in step: ensure /tmp/idem dir)
```

The `(in step: ...)` hint pointed at the **previous** edit's step
name even after the file was rewritten. The line number `1` was
wrong; real problem was at line 17 (`file.template: content:`).

Bisection took ~4 round trips. A user without LLM patience would file
a different bug.

**Fix**: report the line of the offending step, not line 1; report
the offending sub-key when it exists, not the entire allowed-action
vocabulary. Pattern from #30 (step-level errors) is the right shape:

```
Step code (/work/mooncake.yml:8):
  - name: assert command success
    assert:
      cmd:
        cmd: "test -f /tmp/assert-test.txt"
        exit_code: 0
```

## #30 — Step-level validator errors include source location — positive note

**Repro**: when a step-level validation fails (after the file-level
"is this a valid action?" check), error output is:

```
Step code (/work/mooncake.yml:8):
  - name: assert command success
    assert:
      cmd:
        cmd: "test -f /tmp/assert-test.txt"
        exit_code: 0
```

File + line, plus the step YAML quoted back. **Excellent error UX**.
Port this template to the file-level validator (#4).

## #6 — `LLM_GUIDE.md` actions list is out of date — LOW (doc drift)

Line 102 of `LLM_GUIDE.md` says:
> 13 actions: print, vars, shell, command, include_vars, file,
> template, copy, download, unarchive, assert, preset, service

Reality (per `mooncake actions list` and `mooncake schema generate`):
44+ actions with namespaced names (`file.write`, `file.template`,
`text.replace`, etc.). `print`/`include_vars`/`preset`/`command`/`file`/
`template`/`copy`/`download`/`unarchive`/`service` no longer exist as
top-level names.

**Why it matters**: the guide is titled "for LLMs". An LLM following
it verbatim writes a broken playbook. I did, on the first try.

**Fix**: regenerate the action list section from `mooncake docs
generate --section action-summary` (closed by #43).

## #29 — `examples/actions/assert.yml` uses obsolete `cmd:` key — LOW

```
$ mooncake apply -c examples/actions/assert.yml
validation failed for assert action: assert requires one of: command,
  file, http, file_sha256, git_clean, or git_diff
```

The canonical assert example uses `assert: cmd: { cmd: ..., exit_code: 0 }`.
Validator requires `command:`.

**Bonus**: the validator's error message — `assert requires one of:
command, file, http, file_sha256, git_clean, or git_diff` — sets a
quality bar that the file-level validator (#4) doesn't yet meet.
