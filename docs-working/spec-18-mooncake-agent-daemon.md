# Spec 18: Mooncake Agent Daemon (Walking Skeleton)

**Epic:** E7 Mooncake Fleet — distributed mooncake across a trusted network. This
spec is the v1 walking skeleton; follow-ups in Sequencing.
**See also:** `for_later/notes-mooncaked-http-mcp-surface.md` — concrete
HTTP+MCP surface sketch (endpoints, tool schemas, error codes, SSE shape).
Reference target, not a contract; deferred from this spec's scope.
**Effort:** L (~1–2 weeks)
**Value:** Very High — turns mooncake from a single-host CLI into a fleet
runtime that AI agents can drive remotely. Lays the foundation for everything
in the Fleet epic.

---

## Problem

Today mooncake runs as a one-shot CLI invocation against the local machine.
There is no way to:

1. **Apply a plan to another machine** without SSH-wrapping mooncake by hand.
2. **Query live state of another machine** (facts, applied-plan history, drift)
   without shelling in.
3. **Let an AI agent operate a fleet.** Spec 10 exposes mooncake over MCP via
   stdio — great for the local host, useless across machines.

The user case driving this: two trusted machines on a home LAN (Mac + Arch),
both managed by mooncake, both reachable from an AI agent (Claude / Cursor /
etc.) without ad-hoc SSH plumbing.

Spec 10 already gave us a local MCP surface. This spec adds the **long-running
daemon + remote transport + bearer auth** so the same surface works across the
network. Spec 10's tools (`get_facts`, `run_plan`, etc.) become the foundation;
this spec extends the set with apply-from-payload and adds `mooncake fleet …`
CLI sugar so humans can use it too.

---

## Goals

- **G1** Ship `mooncaked`: a long-running daemon installable on Linux and macOS.
- **G2** Expose the existing MCP tool surface over **HTTP+SSE** (remote
  transport), authenticated by a single shared bearer token.
- **G3** Support **remote apply from day one**: a client ships a YAML config +
  vars; the daemon plans and executes locally using its own facts.
- **G4** Add `mooncake fleet apply|facts|status` CLI commands that iterate over
  a static peer list and call MCP under the hood.
- **G5** Persist a local history of applied plans on each node for audit and
  drift detection (later specs).
- **G6** Stay additive — existing `mooncake` CLI behavior is unchanged; stdio
  MCP from Spec 10 keeps working.

**Non-goals (deferred to later specs in E7):**

- Tailscale-native peer identity / per-peer capabilities
- Server-side fleet fan-out (the daemon serves itself; the *client* iterates)
- Streaming execution events (`plan.apply` is blocking in v1)
- Preset bundling in the apply payload (presets must already exist on target)
- Drift reconcile loop / scheduled re-apply
- Multi-node atomic apply or rollback
- mDNS discovery (peer list is static)
- Privilege separation (daemon runs as root)

These are listed in **Sequencing** with rough effort.

## Configuration: `agent.toml`

Single file, same shape on both daemon and client side:

```toml
# Identity & auth
token = "0123abcd…"          # 32 hex chars, generated by `mooncake agent init`

# Daemon-only
[server]
bind     = "0.0.0.0:8765"     # what mooncaked listens on
allow    = ["192.168.0.0/24"] # source-IP allowlist (CIDR); reject otherwise
history  = "/var/log/mooncake/applied.jsonl"

# Client-only
[[peers]]
name = "arch"
addr = "arch.local:8765"

[[peers]]
name = "mac"
addr = "mac.local:8765"
```

Resolution: `--config` flag > `$MOONCAKE_AGENT_CONFIG` > `~/.mooncake/agent.toml`
> `/etc/mooncake/agent.toml`.

The daemon and client deliberately share the same file format so users can copy
one `agent.toml` to every machine. Daemons ignore the `[[peers]]` block;
clients ignore `[server]`. Both read `token`.

## Task 1 — Daemon scaffold (`internal/agent/`)

Build a minimal HTTP server that wraps the existing MCP tool dispatch.

### Subtasks

1. `cmd/agent.go`: register `mooncake agent` with subcommands:
   - `init` — generate a 32-hex token, write `~/.mooncake/agent.toml` (do not
     overwrite if exists; require `--force`).
   - `install` — write `init/mooncaked.service` to `/etc/systemd/system/` (Linux)
     or `init/mooncaked.plist` to `/Library/LaunchDaemons/` (macOS) and enable.
   - `run` — foreground daemon mode (what the unit file invokes).
   - `status` — print bind addr, pid, uptime, last applied plan from history.
2. `internal/agent/server.go`: `net/http` server bound per `[server].bind`.
   Single endpoint `POST /mcp` that speaks the same JSON-RPC the stdio MCP
   server speaks. Reuse `internal/mcp` dispatch verbatim.
3. `internal/agent/auth.go`: middleware that:
   - Rejects any source IP outside `[server].allow` with 403.
   - Requires `Authorization: Bearer <token>` matching `token`; otherwise 401.
   - Constant-time compare on the token.
4. `internal/agent/sse.go`: SSE endpoint `GET /mcp/events?id=<execution_id>`.
   For v1 this is a stub that returns a single `done` event when the
   corresponding `plan.apply` finishes. Real streaming is deferred — but having
   the URL shape stable now keeps later specs additive.

### Privilege model (v1)

The daemon runs as root. The systemd unit uses no `User=` directive. macOS
launchd plist runs from `/Library/LaunchDaemons/` (root context). Document this
loudly in `agent install` output:

```
mooncaked installed. NOTE: daemon runs as root.
Anyone with the agent token has effective root on this host.
Token is in: /etc/mooncake/agent.toml (mode 0600)
```

Privilege separation is a later spec.

## Task 2 — Extend MCP surface for remote apply

Spec 10's tools work on the assumption that the *client* has filesystem access
(`run_plan` takes `{"config": "path/to/config.yml"}`). That breaks across the
network. Add payload-shaped variants:

### New tools (add to `internal/mcp/`)

| Tool | Input | Output |
|---|---|---|
| `apply_yaml` | `{"yaml": "<full config text>", "vars": {…}, "dry_run": bool}` | Same shape as `run_plan` output, plus `execution_id` for log correlation. |
| `check_yaml` | `{"yaml": "<…>", "vars": {…}}` | Same as `check_plan` from Spec 10, but YAML comes in the request. |
| `applied_plans` | `{"limit": int}` | `[{execution_id, started_at, finished_at, changed, ok, skipped, failed, plan_hash}]` from history. |

### Tools that already exist (Spec 10) — reused unchanged

- `get_facts`, `get_snapshot`, `fact_query`, `check_plan`, `run_plan`

`check_plan` and `run_plan` keep their path-based input for local stdio use.
Remote callers should use `check_yaml` / `apply_yaml`.

### Library-shape extractions (confirmed required)

The planner and config reader today are file-coupled. Two small extractions
make them library-shaped enough for the daemon. Both are mechanical refactors
with the existing path-based entry points remaining as 3-line wrappers.

**Extraction 1 — `internal/config/reader.go`**

`ReadConfigWithValidation(path string)` (`reader.go:46`) opens a file with
`os.Open(path)`; everything after line 60 operates on the parsed `yaml.Node`
plus a `locationMap`, with `path` used only for diagnostic display strings.
Split:

```go
// New: takes already-loaded bytes. logicalPath is used only for diagnostic
// display (pass "<inline>" for daemon payloads).
func ReadConfigBytesWithValidation(data []byte, logicalPath string) (*ParsedConfig, []Diagnostic, error)

// Existing function becomes a 3-line wrapper that os.Reads then delegates.
func ReadConfigWithValidation(path string) (*ParsedConfig, []Diagnostic, error)
```

**Extraction 2 — `internal/plan/planner.go`**

`BuildPlan(cfg PlannerConfig)` (`planner.go:144`) is structured around
`cfg.ConfigPath` for three things: reading the file, deriving `CurrentDir`
from `filepath.Dir(cfg.ConfigPath)` (line 189), and tracking input-file
identity for Spec 16's stale-plan check (`seenFiles`, line 198; `HashInputFiles`,
line 217). Add:

```go
// New: parses inline YAML and expands against baseDir. RootFile is set to
// "<inline>"; input-files hash is skipped (daemon does not round-trip plans
// through disk — Spec 18's apply history hash serves as integrity).
func (p *Planner) BuildPlanFromYAML(yamlData []byte, vars map[string]any, baseDir string, tags []string) (*Plan, error)
```

`baseDir` is supplied by the daemon (the `--workdir` flag, default
`/var/lib/mooncake/work`); relative `include:` paths in the inline YAML
resolve from it. Presets continue to resolve via the existing search paths
(`./presets/` from `baseDir`, then `~/.mooncake/presets/`,
`/usr/local/share/mooncake/presets/`, `/usr/share/mooncake/presets/`) — see
`LLM_GUIDE.md`. **Presets must exist on the target node**; bundling is a later
spec.

### Snags to handle in extraction 2

- **Include-cycle detection** (`planner.go:198`) keys on absolute file paths.
  For inline YAML the root has no path. Skip adding the root to `seenFiles`;
  cycles via `include:` are still caught downstream as soon as a real file
  appears.
- **`Spec 16 plan integrity`** (`HashInputFiles`, `GeneratedOn` host facts
  snapshot, `InputFiles` slice) is designed for save-plan / load-plan
  workflows where a plan is built once and applied later. In daemon mode the
  plan is built and executed in one shot, never persisted, so skip the
  input-files hash entirely in `BuildPlanFromYAML`. Spec 18's
  `plan_hash = sha256(yaml + canonicalize(vars))` (Task 3) is the daemon's
  audit hash; it does not need to match Spec 16's format.
- **`plan.RootFile`** is currently the config file path. Set it to `"<inline>"`
  for daemon-built plans. Downstream consumers (executor logging, error
  origins) need to tolerate this string — verify nothing tries to `os.Open` it.

### Plan hash

Compute `sha256(yaml + canonicalize(vars))` and store it on every applied-plan
history record so later drift specs can reference it.

## Task 3 — History log

Append-only JSONL at `[server].history` (default
`/var/log/mooncake/applied.jsonl`). One line per `apply_yaml` invocation.

```jsonl
{"execution_id":"01HW…","started_at":"2026-05-12T19:14:02Z","finished_at":"…","plan_hash":"sha256:…","changed":3,"ok":12,"skipped":1,"failed":0,"caller":"192.168.0.42","dry_run":false}
```

- Rotation: not in v1 (file grows). Document in `agent install` output.
- `caller` is the source IP — the only identity we have without Tailscale.
- `applied_plans` MCP tool reads the tail of this file (last N lines, no full
  scan).

## Task 4 — `mooncake fleet` CLI

Thin client over MCP. No new core logic — these are convenience wrappers that
loop over `[[peers]]` from `agent.toml`.

```
mooncake fleet peers                    # print peer list + reachability
mooncake fleet status                   # per-peer: uptime, last apply
mooncake fleet facts --to arch          # calls get_facts on one peer
mooncake fleet apply config.yml --to arch,mac [--dry-run]
mooncake fleet apply --preset kubectl --params version=1.30 --to mac
```

### Behavior

- `--to` accepts comma-separated peer *names* (from `agent.toml`) or `all`.
- The CLI reads the config file locally, sends YAML over the wire — the daemon
  never touches the local FS of the caller.
- For `--preset`, the CLI does *not* expand the preset client-side. It sends a
  tiny YAML stub (`steps: [{preset: kubectl, parameters: {version: "1.30"}}]`)
  and lets the daemon's existing preset loader resolve it on the target.
- Fan-out is sequential in v1. One peer at a time, fail-fast unless
  `--continue-on-error`.
- Exit code: 0 if all succeeded, non-zero on first failure (or aggregate when
  `--continue-on-error`).

## Acceptance criteria

1. `mooncake agent init` produces a usable `agent.toml` with a 32-hex token.
2. `mooncake agent install && systemctl start mooncaked` starts the daemon on
   Linux; equivalent works on macOS via launchd.
3. From a second machine on the LAN with a copy of the same `agent.toml`:
   ```
   mooncake fleet facts --to arch
   ```
   returns the target's facts JSON.
4. `mooncake fleet apply hello.yml --to arch --dry-run` returns a structured
   would-change list and **does not** mutate the target.
5. `mooncake fleet apply hello.yml --to arch` mutates the target and appends
   one record to `/var/log/mooncake/applied.jsonl`.
6. Wrong token → client sees 401, daemon logs the rejection with source IP.
7. Source IP outside `allow` → client sees 403.
8. Spec 10's stdio MCP still works unchanged (`mooncake mcp` regression test).
9. `go test ./internal/agent/... ./internal/mcp/... ./cmd/...` and `make ci`
   pass.
10. README at `/home/alehatsman/projects/mooncake` gets one paragraph in the
    "What's new" section.

## Risk notes

- **Token = root.** Document loudly. Anyone on the LAN with the token has full
  remote-exec. Acceptable for a home network of one trusted user; not
  acceptable beyond that. Spec 22 (Tailscale identity) is the real fix.
- **Plain HTTP.** No TLS in v1 — bearer token travels in cleartext on the LAN.
  Fine for a trusted home network; document. If users want it earlier than
  Spec 22, a self-signed-cert flag is cheap to add.
- **Library-shape extractions are confirmed mechanical** (see Task 2). The
  config reader and planner today take file paths, but the file-handling code
  is well-isolated at the top of each entry point — splitting into bytes-based
  variants is a 3-line wrapper change in each, plus a small amount of plumbing
  around `RootFile`, `seenFiles`, and the Spec 16 integrity hash. Low risk;
  not a project blocker.
- **macOS launchd path.** `/Library/LaunchDaemons/` requires sudo to install
  and the plist must be owned by root. `agent install` needs to check it's
  running with the right permissions and fail with a useful message
  otherwise.
- **History file ownership.** `/var/log/mooncake/applied.jsonl` is created by
  the root daemon; document that non-root reads need group `mooncake` (or
  similar) — defer until someone asks.
